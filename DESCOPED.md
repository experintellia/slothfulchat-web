# Descoped / postponed

Deliberate omissions from the prototype. Postponed ≠ rejected — each entry says why and what re-enabling takes.

> **Calls** (native 1:1 WebRTC audio/video) were previously descoped here; they are **no longer descoped** and are now in progress — see [`docs/calls.md`](docs/calls.md) (own `packages/calls`, a single thin desktop patch un-gating the call button, phased M0–M5). M0 (interop spec + package scaffold + un-gate patch) has landed.

| What | Why | Re-enabling would take |
|---|---|---|
| P2P backup transfer (iroh) | Browser iroh (0.32+) is relay-only, no LAN connectivity, and DC backup transfer is LAN-restricted, so it can't work. iroh itself runs: webxdc realtime channels use its relay-only transport (WEBXDC.md). | Upstream lifting the LAN restriction. File-based IMEX covers backups meanwhile. |
| the webxdc maps integration | Apps run, realtime channels included (WEBXDC.md, issue #2), but maps.xdc is an integrated webxdc that also needs internet access through core's HTTP, which is stubbed on wasm. Maps are planned differently anyway. | A per-app CSP exception for tile images plus core HTTP routed through fetch — Electron's `internet_access` path — if the upstream maps.xdc is wanted after all. |
| sqlcipher / DB encryption | SQLCipher's vendored OpenSSL doesn't build for wasm32; OPFS is origin-sandboxed anyway. | A wasm-compatible SQLite cipher VFS, or upstream rusqlite wasm support with a different cipher. |
| Web push (notifications while the app is closed) | Only valuable with no tab open — a running tab already gets instant delivery via IMAP IDLE and can notify itself. The naive version (chatmail `devicetoken` metadata → small web-push proxy → generic "new message" notification) fails on silent traffic: Chromium's `userVisibleOnly` forces a visible notification per push, but without decrypting, the SW can't tell a real message from a read receipt, webxdc update, or blocked contact — noise notifications (DC iOS decrypts inside its Notification Service Extension for exactly this reason). Decrypt-in-SW is blocked by architecture: the sahpool VFS needs sync access handles (dedicated workers only, and service workers can't spawn workers), so it would take a second core build on an async VFS, cold-booting the whole core inside the push event's time budget. iOS (declarative web push) never runs SW code, so no previews there regardless. A browser extension could host a persistent core, but that costs extra install/commitment and doesn't exist on mobile. Also: in-wasm HTTP is stubbed, so the core's push-token plumbing is dead code here anyway (FINDINGS). | A web-push proxy service (subscription-as-devicetoken), un-stubbing core HTTP or routing it via fetch/WS, plus a spike: core on an IndexedDB/async-OPFS VFS booting in a service worker fast enough to fetch + decrypt within the push window (Chromium/Android only). |
| In-session sahpool growth (reserve-before-open core patch) | The sqlite pool is sized at boot (`max(32, 2N+8)`, FINDINGS M5); creating ~`N+8`+ accounts in one session without a reload can exhaust it. Degrades gracefully (creation errors, reload re-sizes and recovers), and mass in-session account creation isn't a real user flow — not worth a new core patch (patch-count is the prototype's headline metric). | A small core patch: an async `tokio::fs::reserve_sqlite_slots(n)` call (shim-provided, wasm-cfg'd) at the top of `Sql::open`, so every db open guarantees free slots first. Scoped during the post-#75 CANTOPEN incident (2026-07-12). |
